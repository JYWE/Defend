# 第二阶段战斗白盒实施契约

日期：2026-10-10。用户已授权开发团队实施第二阶段，选择中型规模，要求约 70 度斜俯视角，并确认先在当前电脑验收。本文记录实施选择，不将白盒参数冒充最终玩法平衡。

## 范围与边界

- 目标规模为最多 100 栋未出售建筑、200 个同时存活敌人。波次累计敌人数与同时存活数分开配置。
- 一张约 40×40 白盒地图，五波基础敌人，一种炮塔，准备、战斗、清场奖励、下一波、胜利、核心失败及重新开始。
- 战斗中支持建造、移动、出售、维修和终端优先级调整；核心不允许移动或出售，不能购买第二个核心。失败后不能靠维修撤销败北。
- 原能源试验场保留。新增 `CombatWhitebox.unity`，场景、Prefab 和定义资源可手工编辑；制作工具仅创建缺失资产，不覆盖已有手工内容。
- UI 在场景或 Prefab 中预先完整保存，运行时只绑定和更新；包括敌人血量表现也不通过运行时创建 UI 实现。建筑、敌人、能量与射击几何表现允许实例化已制作 Prefab。
- 不安装额外框架，不提交、推送或重置工作区。所有验证直接比较数值和状态，禁止哈希值校验。

## 本次实施选择

1. 敌人优先前往核心；存在可行通路时绕过建筑。完全封路时，选择当前区域能够接近、朝核心方向的阻挡建筑并攻击。共享网格距离场随建筑占用变化失效；拆障为启发式，不声称求得全局最小拆除代价。多格建筑按一个建筑身份承受伤害。
2. 敌人位置、索敌、攻击、伤害、死亡均由纯 C# 模拟决定。初版不使用 NavMesh 或每个敌人的物理碰撞回调决定权威状态。
3. 炮塔选取射程内目标，冷却完成且缓存足够时整笔扣除每发能量并射击。缺能时不扣部分能量，也不累计补射次数。射击使用即时伤害，射击 Prefab 只表现命中，不决定逻辑结算。
4. 波末奖励仅结算一次，不自动修复建筑或补充护盾。下一波复用同一个世界，保留所有能源状态。重新开始明确创建新世界并恢复编辑器保存的初始布局。
5. 白盒暂沿用即时付费维修及 1 点能量吸收 1 点伤害，炮塔能耗、攻击间隔、敌人速度、波次等均由资源配置。后续改规则需同步实现与测试。
6. 摄像机保留正交投影，俯角相对水平面向下 70 度（Unity 欧拉角 X=70），朝向和位置保存到场景；缩放、拖动围绕地面交点限位。

## 模块契约

- `GameWorld` 构造增加可选第四参数 `BattleSettings`；不传参数时兼容原能源试验场。`Battle` 在非战斗模式为 null。
- `WorldCommand.StartWave()` 按正常命令时序执行。战斗模式关闭测试负载，由真实攻击消费能量。
- `BattleSystem` 提供只读状态、敌人、短期射击记录、波次、奖励和生成进度；表现不得直接修改生命、能量、金钱。
- `GameSessionRoot` 负责新建会话、重开、输入和表现组合。首次初始化记录场景初始建筑，重开不能使用被玩家移动后的坐标。
- 能源与战斗分别拥有内部状态，战斗消费调用现有能源接口，建筑受损复用世界生命周期接口；能源不读取波次状态。

## 验证目标

当前机器：Intel Core i9-14900HX、NVIDIA GeForce RTX 4060 Laptop GPU、约 32 GB 内存。最低硬件配置尚未认证。

在正常一倍速、1920×1080 独立 Player 下，以 60 帧/秒为目标；建议预算为帧耗时 p95≤16.7 毫秒、p99≤25 毫秒，整个模拟单步 p95≤6 毫秒、p99≤10 毫秒。20 Hz 是逻辑频率，不意味着模拟可以独占主线程 50 毫秒。未达到时必须保留失败数据并解释，不以降低实际供给掩盖性能问题。

验证包括原能源回归、战斗边界、五波流程、失败及重开、70 度镜头、输入防穿透、UI 无运行期生成、资源引用、Windows 构建与实际可见画面。中型规模测量同时报告建筑数、敌人数、连接密度、活动能量批次、寻路积压、供给与实际模拟推进。长期检查区分模拟时间和现实运行时间，不将加速纯模拟冒充真实 Player 长时间测试。

团队由战斗模拟、场景界面、能源性能三组并行实施；主负责人独占 Unity Editor 的编译、资产生成、测试和构建，负责跨模块测试、独立 Player 验收及最终报告。
