# 第二阶段能源性能与长期规则检查

日期：2026-10-10。这里的记录来自 Windows 上的 .NET 9.0.12 独立控制台进程，**不是 Unity Editor 或独立 Player 帧率证据**。没有增加 Unity 包、执行哈希值校验、减少能源吞吐预算、删除历史或跳过原有行为断言。

## 可复现入口

```powershell
# 固定第一阶段世界，只替换能源模块；200 步预热后测量 200 步。
Tools/Performance/RunEnergyProbe.ps1 -Count 100 -Warmup 200 -Steps 200 -OutputPath final-100.json
Tools/Performance/RunEnergyProbe.ps1 -Count 100 -Warmup 200 -Steps 200 -Baseline -OutputPath baseline-100.json

# 只在临时源码中加入 Stopwatch 分段采样，不污染运行时代码。
Tools/Performance/RunEnergyProbe.ps1 -Count 100 -Warmup 200 -Steps 200 -Profile -OutputPath phases-100.json

# 36000 个逻辑步对应 20 Hz 下 30 分钟模拟时间，不是等待 30 分钟墙钟时间。
Tools/Performance/RunEnergyProbe.ps1 -Count 100 -Warmup 200 -Steps 36000 -OutputPath stability-100.json
Tools/Performance/RunEnergyLongFairness.ps1 -OutputPath fairness.txt
```

`EnergyBaselineSource.zip` 保存优化之前的纯 C# 模拟源码，确保前后使用相同的第一阶段世界与定义。控制台项目、编译产物和注入的诊断均创建在系统临时目录。性能入口关闭 .NET 分层即时编译，并在调用后恢复环境变量。工程仍由 Unity 使用原有程序集编译，不依赖这些工具。

公平性入口读取工程原有的优先级测试，只在临时副本中将长期统计窗口扩大到 36000 步，仍保留原有份额容差和 80% 吞吐下限。NUnit 使用工程已有包，不另外安装依赖。

## 定位与实现

分段证据：`stage-profile-before-100.json`、`stage-profile-after-100.json`。原始主要成本集中于调度中的动态候选报价与待处理寻路队列。对照平均每步调度部分约 10.244 → 1.448 毫秒，寻路队列约 5.755 → 5.072 毫秒；这些是带探针的 .NET 墙钟测量，不可换算成 Unity CPU 保证。最终剩余主要热点仍是寻路工作。

已完成的能源内部调整：

- 每步开始采集中继可用状态，发送时只刷新两个受影响端点，取消每次动态寻路报价中的全图扫描。
- 相同实际访问前缀复用不可变历史对象。复用索引最多 4096 项，索引淘汰不修改批次持有的历史或累计滞留时间。
- 搜索候选使用二叉最小堆；完成的无约束反向路径树为历史约束查询提供 A* 损耗下界。未完成的树不会被用作启发函数。
- 历史查询完成时将路线转为独立边数组，临时搜索集合清空后复用，空闲工作集合上限为 64。反向共享树保持自身数据；在途路线不引用已清空的查询集合。
- 同一动态查询替换旧版本时同步删除旧年龄记录，避免旧版本挤走有效缓存。
- 修正长期份额偏差：发生实际发送后推进轮次时，所有已登记存活账户按权重增加额度并保留未用余额；最多保存两轮。没有发送进展时不累加，优先级变化仍限制旧余额。

能源公开接口保持不变，权重仍为 1/2/4。原来的 70 点供给示例、需求上限、路径历史、拆分预算、到货延迟、移动和销毁行为继续使用原断言检查。没有提高每步寻路预算或交易预算。

## 密集方阵前后对照

场景参数与第一阶段规模测试一致：100/400/1600 建筑，四分之一反应堆、二分之一中继、四分之一炮塔，半径 7 格，每炮塔每步需求 1000 最小单位。分别预热 200 步，再测 200 步。数据文件为 `comparison-before-*.json` 和 `comparison-after-*.json`。

| 建筑数 | 有向连接 | .NET 单步 p95，之前 → 最终（毫秒） | 测量期消费占需求，之前 → 最终 | 最终待规划，之前 → 最终 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 4072 | 21.40 → 17.45 | 92.6% → 97.1% | 981 → 85 |
| 400 | 24166 | 88.32 → 17.35 | 68.4% → 62.8% | 2148 → 2148 |
| 1600 | 114126 | 117.60 → 14.66 | 35.1% → 32.3% | 2495 → 2303 |

所有最终记录守恒差额为 0。100 建筑最终批次峰值为 1249，全部 25 个终端曾收到能量。400 建筑全部 100 个终端曾收到能量，1600 建筑为 364/400。**400 和 1600 的耗时下降同时伴随供给下降，不能称为达标或总体性能改善。100 建筑的 .NET 数值也没有满足建议的能源 3 毫秒或完整模拟 6 毫秒预算。**

短窗口仍含供给建立与拥堵变化，不能代替稳态。开发电脑在本轮还承担其他构建任务，因此墙钟耗时会受调度和温度影响；最终性能结论应使用独占目标机器的 Unity/Player 测量。

`receivedAtAllNodes` 是包括中继在内的各节点累计到货增量，不能当作终端有效供给总量；表中的供给比例使用实际终端消费。分配字节统计包含探针周期内的诊断，不代表零开销的模拟独占分配量。

## 长期公平性

`baseline-long-fairness.txt` 暴露原先短窗口未覆盖的问题：共享中继、近端效率约 0.944444、远端效率 0.5、相同权重时，36000 步的有效到货为 36474351 / 34647552，比值 1.052725，超出原有 5% 容差。旧算法在原始输出尾数不足时，只给已耗尽额度的一端续发新轮次；`fairness-diagnostic-before.txt` 记录了两端累计获额差异。

修正后的 `final-long-fairness.txt`：

- 原有八组优先级检查全部通过，长期场景使用 36000 步窗口。
- 共享中继 4:2:1：72000000 / 36000000 / 18000000，保持精确比例，低优先级持续获能。
- 共享源头 4:2:1：144000000 / 72000000 / 36000000。
- 不同损耗相同权重：35282067 / 35282443，比值约 0.999989；中继原始输出 107988723 / 108000000，约 99.99%。原有 5% 误差与 80% 吞吐下限均保持不变。
- 70 点有限供给、需求上限、运行中改优先级、不可达目标检查继续通过。

最终能源版本还在独立 .NET 进程执行了第一阶段全部 47 项原始断言，47/47 通过，记录为 `final-original-rules.txt`。Unity 中的集成测试应以主负责人生成的记录为准。

## 30 分钟固定拓扑稳定性

`final-long-stability-100.json` 使用最终版本、100 个密集建筑，200 步预热后运行 36000 步：

- 实际消费 899808740 / 900000000，约 99.9787%，守恒差额 0。
- 批次峰值 2131；每 2000 步记录的批次数为 1260–1696，待规划数为 0–362；结束时 1443 批次、0 待规划。
- 每 2000 步诊断时主动回收后的保留托管内存约 11.9–25.9 MB，在该窗口内未观察到持续上升。回收在计时范围外，因此这些样本不能证明 Player 中没有回收停顿。
- 单步 p95 10.232 毫秒，p99 22.568 毫秒；每步平均约 1.20 MB 分配，仍需优化。

这证明固定密集网络在该模拟窗口中的供给与数量稳定，不包含反复无限新建/出售、长期战斗、Unity 表现或真实 30 分钟 Player 试玩。全图拓扑变化仍会重建路线缓存；更细的拓扑失效范围、动态查询工作成本和临时分配仍是后续热点，不能用本报告宣称所有性能验收已完成。
